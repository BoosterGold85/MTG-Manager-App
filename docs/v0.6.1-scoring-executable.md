# EXECUTABLE: REBUILD DECK DNA SYNERGY SCORING

## Objective

Replace the current shallow tag-overlap synergy calculation with a deck-aware scoring model that evaluates whether a candidate card actually improves the specific Commander deck.

The current system is overvaluing generic tags such as:

- Card Advantage
- Spells
- Combat
- Removal
- Ramp

This caused cards such as:

- Alania's Pathmaker
- Harnesser of Storms
- Mongoose Lizard

to appear as meaningful recommendations for the Reign of Dragons Commander deck.

These cards may technically share generic tags with cards already in the deck, but they do not materially advance the deck's primary Dragon strategy.

The new engine must distinguish:

**generic usefulness**

from

**actual deck synergy**

---

# 1. DO NOT REMOVE THE EXISTING DECK DNA SYSTEM

Preserve:

- current deck import
- collection ownership logic
- card database
- card detail view
- recommendation UI
- card tags
- role identification
- owned printing / variant logic
- sorting and filtering
- current deck analysis where usable

This is a scoring-engine replacement, not a redesign of the Deck screen.

---

# 2. NEW CORE PRINCIPLE

Synergy score must answer:

> "How much does this card strengthen what THIS deck is specifically trying to do?"

It must NOT primarily answer:

> "How many tags does this card share with the deck?"

Generic tag overlap should become only a small portion of the final score.

---

# 3. CREATE A DECK STRATEGY PROFILE

For every Commander deck, calculate a structured `DeckStrategyProfile`.

Example:

```ts
type DeckStrategyProfile = {
  commander: Card;
  colorIdentity: string[];

  primaryArchetypes: WeightedTag[];
  secondaryArchetypes: WeightedTag[];

  commanderMechanics: WeightedTag[];

  creatureTypes: WeightedTag[];
  mechanicalThemes: WeightedTag[];

  roleNeeds: DeckRoleNeeds;

  manaCurve: ManaCurveProfile;

  cardTypeDistribution: CardTypeDistribution;

  synergyPackages: SynergyPackage[];

  powerBaseline: number;
};
```

Example for a Dragon deck could evaluate to:

```ts
primaryArchetypes = [
  { tag: "Dragons", weight: 1.0 },
  { tag: "Creature Typal", weight: 0.95 },
  { tag: "Creature ETB", weight: 0.75 },
  { tag: "Creature Cast", weight: 0.70 }
];

secondaryArchetypes = [
  { tag: "Tokens", weight: 0.75 },
  { tag: "Direct Damage", weight: 0.65 },
  { tag: "Big Mana", weight: 0.65 },
  { tag: "Haste", weight: 0.55 }
];

roleNeeds = {
  ramp: "HIGH",
  cardAdvantage: "MEDIUM",
  removal: "MEDIUM",
  protection: "MEDIUM",
  boardWipes: "LOW",
  lands: "LOW"
};
```

These values must be inferred from the actual deck.

Do not hardcode "Dragon deck" behavior.

# 4. COMMANDER MUST BE THE STRONGEST SIGNAL

Analyze the commander separately from the remaining 99 cards.

Extract:

- creature type
- triggered abilities
- activated abilities
- keywords
- token generation
- card types referenced
- permanent types referenced
- cast triggers
- ETB triggers
- death triggers
- attack triggers
- combat triggers
- counters
- sacrifice
- graveyard usage
- spell types
- tribal references
- mana generation
- cost reduction
- copying
- recursion
- card draw
- damage triggers

Generate `CommanderSynergyTags`.

Example concept:

If commander text effectively says:

> Whenever another Dragon enters...

Then cards that are Dragons should receive strong positive weighting.

A random creature that draws a card must NOT receive equivalent weighting merely because "Card Advantage" is a deck need.

---

# 5. NEW 100-POINT SYNERGY MODEL

Final candidate synergy score should be normalized to:

```text
0–100
```

Use the following weighting as the starting model.

## A. COMMANDER SYNERGY — 0 TO 30

Evaluate direct interaction with the commander.

Examples:

- triggers commander
- commander triggers candidate
- candidate improves commander ability
- candidate copies / doubles commander effect
- candidate creates resources commander specifically wants
- candidate belongs to commander-referenced creature type

Score:

```text
0 = no meaningful relationship
10 = weak indirect relationship
20 = strong relationship
30 = direct engine piece
```

---

# 6. PRIMARY ARCHETYPE FIT — 0 TO 25

Evaluate whether the candidate belongs in the dominant strategy of the deck.

For example, in a Dragon typal deck:

Dragon creature:
strong positive

Dragon cost reduction:
strong positive

Dragon token payoff:
strong positive

generic red creature:
little or no positive score

Example:

```ts
archetypeFit =
  sum(candidateTagMatch * deckTagWeight)
```

Normalize to:

```text
0–25
```

---

# 7. ROLE NEED — 0 TO 15

Determine what the deck is actually missing.

Possible roles:

- Ramp
- Card Advantage
- Removal
- Board Wipe
- Protection
- Graveyard Hate
- Tutors
- Recursion
- Finishers
- Lands
- Mana Fixing
- Token Generation
- Sacrifice Outlet
- Payoff
- Enabler

A candidate receives role points only if the role is actually needed.

Example:

If deck has:

```text
5 ramp cards
```

and target is:

```text
10 ramp cards
```

then Ramp need is high.

If deck already has:

```text
15 card advantage pieces
```

then another generic draw card receives very little Role Need score.

Normalize:

```text
0–15
```

---

# 8. SYNERGY PACKAGE MATCH — 0 TO 10

Detect card clusters already operating within the deck.

Examples:

Dragon ETB package:

```text
Dragon Tempest
Scourge of Valkas
Warstorm Surge
Lathliss
```

A new Dragon contributes to all four.

Therefore it receives strong package synergy.

Possible packages:

- Aristocrats
- Spellslinger
- Landfall
- +1/+1 Counters
- Equipment
- Auras
- Reanimator
- Tokens
- Treasure
- Blink
- Dragons
- Elves
- Goblins
- Enchantress
- Artifacts
- Graveyard
- Sacrifice
- Lifegain

Normalize:

```text
0–10
```

---

# 9. CARD QUALITY / EFFICIENCY — 0 TO 10

A card should not rank highly simply because it technically fits.

Evaluate relative quality based on:

- mana efficiency
- effect size
- repeatability
- flexibility
- resilience
- card advantage
- board impact
- relevant EDH power expectations

This does NOT need to become a global "best card database."

Use available card characteristics and contextual comparisons.

Normalize:

```text
0–10
```

---

# 10. GENERIC TAG OVERLAP — 0 TO 5

This is where the CURRENT scoring behavior should largely move.

Examples:

```text
Spells
Combat
Card Advantage
Removal
Creatures
Damage
```

Generic overlap should help break ties.

It should NOT drive recommendations.

Maximum:

```text
5 points
```

---

# 11. CURVE / MANA FIT — 0 TO 5

Evaluate:

- mana value
- deck curve
- color requirements
- ramp profile
- commander cost
- current density at candidate's mana value

Example:

A six-mana card in a deck already overloaded with six and seven-mana cards should receive reduced points.

Normalize:

```text
0–5
```

---

# 12. ADD NEGATIVE MODIFIERS

This is critical.

The current model appears to mostly add positive points.

The new engine must also subtract points.

Possible penalties:

## OFF-ARCHETYPE CREATURE

```text
-5 to -20
```

Example:

A random non-Dragon creature in a strongly Dragon-typal deck.

Do NOT automatically penalize utility creatures if they provide exceptional value.

---

## NO COMMANDER INTERACTION

For decks heavily dependent on commander interaction:

```text
0 to -10
```

---

## REDUNDANT ROLE

Example:

Deck already has excessive card draw.

Candidate's primary purpose is more card draw.

```text
0 to -8
```

---

## CURVE CONGESTION

```text
0 to -8
```

---

## LOW IMPACT FOR MANA VALUE

```text
0 to -10
```

---

## ANTI-SYNERGY

Example:

Candidate exiles graveyards in a graveyard deck.

Candidate sacrifices creatures in a strategy that needs specific creatures alive.

Candidate wipes artifacts in an artifact deck.

```text
0 to -25
```

Anti-synergy must be capable of overriding generic matching tags.

---

# 13. FINAL FORMULA

Initial implementation:

```ts
rawScore =
  commanderSynergy +
  archetypeFit +
  roleNeed +
  packageMatch +
  cardQuality +
  genericOverlap +
  curveFit -
  penalties;
```

Then clamp:

```ts
finalScore = Math.max(0, Math.min(100, rawScore));
```

Do not force scores into an artificial distribution.

If only two cards in the user's collection are genuinely good recommendations, it is acceptable for only two cards to score highly.

---

# 14. SCORE INTERPRETATION

Use:

```text
90–100 = Exceptional Fit
80–89  = Excellent Fit
70–79  = Strong Fit
60–69  = Good Fit
50–59  = Situational
40–49  = Weak Fit
25–39  = Poor Fit
0–24   = Not Recommended
```

Important:

A score of 35 should NOT look like a positive recommendation.

Currently "Synergy 35" visually feels like the app is endorsing the card.

Change the language accordingly.

Example:

```text
Synergy 35
Poor Fit
```

# 18. INVENTORY CANDIDATE FILTERING

Deck DNA currently recommends cards from the user's owned collection.

Preserve this.

However, change candidate ordering.

Default sort should be:

```text
Final Synergy Score DESC
```

Do not surface every legal card as though it is a real recommendation.

Create recommendation tiers.

### Recommended

```text
Score >= 70
```

### Worth Considering

```text
Score 50–69
```

### Other Legal Cards

```text
Score < 50
```

Cards under 50 should be collapsed by default.

This prevents the UI from presenting weak cards as meaningful deck upgrades.

---

# 19. CARD TYPE / TRIBAL CONTEXT

Creature type matching needs additional weight in strongly typal decks.

Calculate:

```ts
tribalDensity =
  cardsMatchingPrimaryCreatureType /
  totalRelevantCreatures
```

Example:

If a deck is heavily Dragon based:

```text
tribalDensity > 0.60
```

then off-tribe creatures should face increasing scrutiny.

Possible penalty:

```ts
offTribePenalty =
  tribalDensity * offTribeBasePenalty
```

BUT:

Do not punish high-value utility cards simply because they are off tribe.

Example utility exceptions:

- extreme ramp efficiency
- powerful card draw
- essential protection
- tutors
- premium removal
- exceptional synergy pieces

# 21. TEST CASE: REIGN OF DRAGONS

Use the current Reign of Dragons deck as a regression test.

The existing recommendations shown during beta testing included:

```text
Alania's Pathmaker
Harnesser of Storms
Mongoose Lizard
```

After this scoring rebuild:

These cards should NOT appear in the primary recommendation tier unless there is some deck-specific interaction we have failed to detect.

Expected:

```text
All three should likely score below 50.
```

At least one should likely score below 30.

Cards that:

- are Dragons
- produce Dragons
- reduce Dragon costs
- reward Dragons entering
- reward Dragons attacking
- create mana for Dragons
- provide meaningful Dragon-specific card advantage

should normally outrank those three.

# 24. DO NOT USE CARD PRICE IN SYNERGY

Price must NOT increase or decrease synergy.

A $0.25 card may be a perfect deck fit.

A $50 card may be terrible for the deck.

Keep:

```text
SYNERGY
```

separate from:

```text
PRICE
```

Later we can create:

```text
Upgrade Value
```

which considers both.

Do NOT combine them now.

---

# 25. DO NOT USE OWNED QUANTITY AS SYNERGY

Ownership determines:

```text
whether the player can add the card
```

It does NOT determine:

```text
whether the card is synergistic
```

Keep those systems independent.

---

# 26. PERFORMANCE REQUIREMENT

Deck DNA must remain responsive on mobile.

Do not repeatedly recalculate complete deck DNA for every card render.

Recommended architecture:

```text
Deck imported
↓
Build DeckStrategyProfile once
↓
Cache profile
↓
Score candidate pool against profile
↓
Cache card scores
↓
Render UI
```

Recalculate when:

- deck changes
- commander changes
- candidate card data changes
- recommendation settings change

Do NOT recompute full deck analysis during scrolling.

# 28. IMPORTANT PRODUCT PRINCIPLE

The recommendation engine should behave less like:

> "These cards contain similar keywords."

and more like:

> "I understand what your deck is trying to accomplish, I understand what it currently lacks, and these are the cards you own that most improve that plan."

That is the goal of Deck DNA.

---

# 29. IMPLEMENTATION PRIORITY

Build in this order:

1. `DeckStrategyProfile`
2. Commander interaction detection
3. Primary archetype weighting
4. Role-need calculation
5. Negative modifiers
6. New 100-point scoring calculation
7. Score explanations
8. Recommendation tier UI
9. Debug score breakdown
10. Regression testing across multiple Commander archetypes

Do not spend time polishing recommendation animations or visual styling until scoring quality passes regression testing.

The scoring engine is currently the limiting factor, not the UI.
