Begin MTG Manager v0.4.0 — Commander Library

First review the current main baseline and existing roadmap/docs before making changes.

Treat v0.3.2 as approved and frozen. Preserve:
- ManaBox import/re-import behavior
- importer reliability/recovery
- collection management
- Card Intelligence
- manual tag overrides
- Keywords filtering
- Name / Oracle Text / All search
- current visual identity/design tokens
- current PWA/app icon assets
Do not refactor approved systems unless required for Commander Library integration.
Goal
Turn MTG Manager from an intelligent binder into a personal Commander deck library.

The user should be able to:
1. Create a Commander deck.
2. Choose its commander.
3. Add owned cards from the collection.
4. Track which physical copies are assigned to which decks.
5. View and edit a saved deck later.
6. Immediately understand basic deck composition without introducing Deck DNA yet.
This release establishes the deck/copy architecture that later versions will use for Deck DNA, owned-card recommendations, new-set matching and playgroup comparison.
1. Commander Library
Add a new primary navigation destination:

Decks

The Decks screen should visually match the premium binder design.

Each saved deck card should show:
- Commander artwork
- Deck name
- Commander name
- Commander color identity
- card count
- owned/assigned status
- last modified
Keep the presentation artwork-first and mobile-friendly.

Do not turn this into a spreadsheet/table interface.

Empty state:

“Build your first Commander deck.”

Primary action:

New Deck
2. Create Deck
New Deck flow:
Step 1 — Deck name
User enters a custom deck name.
Step 2 — Commander
Let the user search their collection for a commander.

Initial commander candidates should be cards that can reasonably be commanders based on canonical Scryfall metadata, such as:
- legendary creatures
- cards explicitly stating they can be your commander
Preserve architecture for multiple-commanders/Partner-style decks even if advanced legality validation remains limited.

Do not infer commander eligibility from tags.

Use canonical card metadata.

Once selected, store:
- canonical card identity
- selected physical printing/copy where applicable
- commander name
- color identity
Commander color identity becomes the deck's primary legality boundary.
3. Deck Editor
The deck editor should remain usable one-handed on mobile.

Top section:
- deck name
- commander artwork/name
- color identity
- deck card count
- Edit Deck / overflow controls
Primary sections:

Commander

Deck

Add Cards

Do not introduce Deck DNA yet.

Basic deck statistics are acceptable:
- total cards
- lands
- creatures
- artifacts
- enchantments
- instants
- sorceries
- planeswalkers/battles if present
- average mana value
Keep those secondary to the actual cards.
4. Add Cards From Collection
The Add Cards experience should reuse the approved collection browsing architecture where practical.

User should be able to search/filter owned cards by:
- name
- tags
- keywords
- color
- Commander Colors
- type
- mana value
Only Commander-color-legal cards should appear by default.

Provide an explicit way to view incompatible cards if useful, but do not silently add them.

Card tiles should clearly show:
- quantity owned
- quantity already assigned
- quantity available
Example:

Owned 3 · Assigned 2 · Available 1

Adding a card should allocate a physical owned copy to this deck.
5. Physical Copy Allocation
This is a critical architecture requirement.

MTG Manager must distinguish:

card identity

from

physical copies owned

from

copies assigned to decks

The user normally keeps separate physical copies in separate Commander decks.

Therefore:

Never silently move a copy from one deck to another.

Example:

User owns:

Sol Ring ×3

Deck A uses 1.

Deck B uses 1.

Available:

1

If all three are already allocated, attempting to assign another owned copy must not automatically remove one from another deck.

Instead show something like:

No unassigned copy available

and identify the decks currently using the copies.

The user can then explicitly choose what to do.

For v0.4.0, favor correctness over sophisticated proxy/wishlist handling.

Do not invent an automatic deck-transfer system.
6. Printing-Level Ownership
Preserve printing-level information.

If the user owns multiple versions of the same card, assignments should be able to reference the actual owned printing/copy group rather than only the card name.

Example:

Sol Ring — Fallout

versus

Sol Ring — Commander Masters

Deck allocation must not destroy:
- set
- collector number
- finish
- language
- condition
- quantity
Do not duplicate collection records merely because a card was added to a deck.

Deck assignment is a relationship to ownership.
7. Removing Cards From Decks
Removing a card from a deck:
- removes only the assignment
- returns that owned copy to Available
- does NOT remove it from Collection
- does NOT modify ManaBox
UI copy should make this distinction clear.

Likewise:

Deleting a deck must never delete collection cards.

Confirm deck deletion.
8. Collection Integration
Card Detail should gain a small new ownership section:

Deck Usage

Example:

Owned: 3

Available: 1

Used in:
- Zombie Deck
- Atraxa Counters
This should be informational and subordinate to Card Intelligence.

Clicking a deck may navigate to that deck.

Do not redesign Card Detail.
9. Re-import Safety
ManaBox re-import must remain safe.

A normal re-import must not destroy deck assignments.

Reconciliation should continue using stable/canonical ownership identity wherever possible.

If a re-import means fewer physical copies now exist than are assigned across decks:
- do not silently move assignments
- do not silently delete assignments
- surface an allocation conflict
Example:

Owned: 1

Assigned: 2

Show that the inventory needs reconciliation.

This should be explicit and recoverable.
10. Persistence / Data Model
Introduce a durable deck repository boundary consistent with the existing CollectionRepository approach.

Suggested concepts:

Deck

DeckCommander

DeckCardAssignment

Avoid storing duplicate full card metadata inside every deck when canonical references can be used.

Deck data should survive:
- refresh
- browser close
- app restart
- normal collection re-import
- intelligence recalculation
Schema should anticipate future:
- Deck DNA
- upgrade suggestions
- deck history
- multiple commanders
- playgroup sharing
But do not implement those features now.
11. Backup
Update MTG Manager JSON backup so it contains:
- saved decks
- commander selections
- card assignments
- printing references
Do not break existing collection backup fields.

Restore/import of backup is still not required unless already supported.
12. Commander Legality
At minimum enforce:

Color identity

Cards whose color identity contains colors outside the commander's identity should not be normally addable.

Colorless cards remain legal.

Use canonical color_identity.

Do not attempt to build a complete MTG rules/judge engine in v0.4.0.

If legality beyond color identity is uncertain, surface a warning rather than inventing certainty.
13. UX Principles
Preserve the existing design system:
- Obsidian Olive background
- parchment text
- antique-gold accents
- artwork dominant
- restrained borders
- progressive disclosure
- mobile first
Avoid:
- giant stat dashboards
- spreadsheet layouts
- excessive deck analytics
- dense desktop-first editing screens
The core task should be:

Open deck → add/remove card → understand ownership → done.
Explicitly Out of Scope
Do NOT implement yet:
- Deck DNA
- archetype percentages
- AI deck summaries
- upgrade recommendations
- “cards you own that improve this deck”
- new-set recommendations
- EDHREC comparison
- deck uniqueness scoring
- playgroup accounts
- cloud sync
- public deck sharing
- pricing
- automatic card movement between decks
Those belong to later roadmap versions.
Required Tests
Add deterministic tests covering at minimum:
1. Create deck.
2. Select commander.
3. Commander color identity restricts candidate cards correctly.
4. Add owned card.
5. Assignment survives reload.
6. Same canonical card can be assigned to multiple decks when enough physical copies exist.
7. Cannot silently over-allocate copies.
8. Removing from deck returns availability without removing collection ownership.
9. Deleting deck leaves Collection untouched.
10. Different printings remain distinguishable.
11. ManaBox re-import preserves valid deck assignments.
12. Reduced ownership surfaces an allocation conflict rather than deleting assignments.
13. Collection Card Detail accurately shows deck usage.
14. Existing v0.3.2 tagging/keywords/search remain unchanged.
15. Existing v0.3.1 interrupted-import recovery remains green.
