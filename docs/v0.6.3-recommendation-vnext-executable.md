# MTG Manager — Deck Upgrade Recommendation Engine vNext

## Purpose

Rework the owned-card recommendation engine so that recommendations are based on **actual Commander/deck interactions**, not broad keyword similarity.

The current system has improved at surfacing interesting candidates, but it still over-scores cards when they share generic labels such as:

- Tokens
- Tutor
- Ramp
- Dragons
- Sacrifice
- Counters

These broad categories are useful for finding candidate cards, but they are **not sufficient evidence of synergy**.

The goal of this pass is to make recommendation scores:

1. mechanically defensible;
2. commander-aware;
3. deck-aware;
4. role-aware;
5. appropriately penalized;
6. explainable;
7. calibrated so that 80+ actually means something.

Do not redesign the UI or broader MTG Manager architecture during this pass unless required for the scoring/explanation changes below.

---

# 1. Core Design Principle

Replace:

`CARD → TAGS → SIMILARITY → SCORE`

with:

`CARD → FACT EXTRACTION → TYPED EFFECTS → COMMANDER INTERACTION → DECK INTERACTION → ROLE NEED → CURVE/REDUNDANCY → PENALTIES → SCORE → SWAP TARGET → EXPLANATION`

Generic tags may still be used to identify possible candidates.

Generic tags must **not independently create large synergy bonuses**.

---

# 2. Separate Card Facts From Interpretation

Every candidate card should first be converted into factual structured data.

Example:

```ts
interface CardFacts {
  name: string;

  manaValue: number;
  colors: string[];

  cardTypes: string[];
  creatureTypes: string[];

  keywords: string[];

  createsTokens?: {
    count?: number;
    tokenTypes: string[];
    creatureTypes?: string[];
  }[];

  searchesLibrary?: {
    targetTypes: string[];
    destination:
      | "hand"
      | "battlefield"
      | "graveyard"
      | "top"
      | "other";
    restrictions?: string[];
  }[];

  drawsCards?: boolean;

  addsMana?: {
    amount?: number;
    colors?: string[];
    restrictions?: string[];
  }[];

  removal?: {
    permanentTypes?: string[];
    targetRestrictions?: string[];
  }[];

  triggers?: string[];
  staticEffects?: string[];

  hasChangeling?: boolean;
}
```

This layer must describe what the card actually does.

It should not yet decide whether that action is good for the deck.

# 3. Replace Broad Roles With Typed Roles

Broad roles may remain as parent categories, but scoring must use more specific subtypes.

## Tutor

Replace one generic `tutor` classification with:

```text
unrestricted_tutor
creature_tutor
dragon_tutor
tribal_tutor
artifact_tutor
enchantment_tutor
land_tutor_to_hand
land_tutor_to_battlefield
basic_land_to_hand
basic_land_to_battlefield
graveyard_tutor
topdeck_tutor
```

Important:

Fetching a basic land into hand is **not equivalent** to a normal tutor.

Do not give `basic_land_to_hand` the same role value as an unrestricted tutor.

---

## Tokens

Replace generic `token_generation` with:

```text
dragon_token
tribal_relevant_token
generic_creature_token
soldier_token
treasure_token
clue_token
food_token
copy_token
token_doubler
token_payoff
token_sacrifice_payoff
```

Token type matters.

A deck that rewards Dragon tokens should not receive a major bonus because a card produces Soldiers.

---

```text

```

These effects have substantially different value.


# 4. Commander Interaction Engine

Add a dedicated Commander Interaction evaluation before general deck synergy is scored.

The engine should determine:

> Does this candidate card actually trigger, enable, amplify, protect, or exploit the commander's rules text?

Do not award commander-interaction points merely because the candidate shares a creature type or broad theme.

---

## Commander Interaction Score

Score from:

`0–25`

Suggested interpretation:

```text
25 = extremely direct/high-value commander interaction
20–24 = strong direct interaction
15–19 = meaningful repeatable interaction
10–14 = useful indirect interaction
5–9 = minor/incidental interaction
1–4 = technically related but negligible
0 = no meaningful interaction
```

Every nonzero commander score must have stored evidence.

Example:

```ts
interface CommanderInteraction {
  score: number;
  direct: boolean;
  evidence: string[];
}
```

---

# 5. Mandatory Interaction Validation

Before claiming that a card:

- triggers the commander;
- reinforces the commander;
- benefits from the commander;
- creates a relevant token;
- satisfies a tribal payoff;

the engine must validate the actual rules relationship.

Example for Lathliss:

Commander condition:

```text
Whenever another nontoken Dragon enters the battlefield under your
control, create a 5/5 red Dragon creature token with flying.
```

Candidate:

```text
Changeling Wayfinder
hasChangeling = true
```

Because changeling makes the creature every creature type:

```text
candidate qualifies as Dragon
candidate is nontoken
candidate entering satisfies commander trigger
```

Result:

```ts
{
  direct: true,
  score: 23,
  evidence: [
    "Changeling makes Changeling Wayfinder a Dragon.",
    "Its entry therefore triggers Lathliss."
  ]
}
```

---

# 6. Typed Token Matching

Token generation must compare the generated token type against the deck's supported token types.

Example:

Deck priority:

```text
dragon_token: HIGH
generic_creature_token: LOW
soldier_token: NONE
```

Card:

```text
Fire Nation Attacks
creates two Soldier tokens
```

Result:

```text
token generation exists
BUT
tokens do not match Dragon tribal strategy
```

Therefore:

```text
No Dragon-token synergy bonus.
No Lathliss trigger.
No "directly reinforces Commander" claim.
```

Generic token production may still receive minor utility credit if appropriate, but not tribal credit.

---

# 7. Role Need Must Be Separate From Synergy

A card can be good because the deck needs its function even if it has zero commander synergy.

Create separate scoring components for:

```text
Commander Interaction
Deck/Theme Interaction
Role Need
Card Efficiency
Curve Fit
Existing-Card Interaction
```

Do not combine role need and synergy into one category.

Example:

Chaos Warp may have:

```text
Commander Interaction: 0
Dragon Synergy: 0
Role Need: high
Card Efficiency: high
```

It may still be recommended because removal is needed.

That is desirable.

---

# 8. Proposed Score Model

Normalize the positive portion to 100 before applying penalties.

Recommended starting weights:

```text
Commander Interaction        25%
Deck / Theme Interaction     20%
Needed Role                  20%
Card Quality / Efficiency    15%
Mana Curve Fit               10%
Existing-Card Interaction    10%
```

Then:

```text
Final Score =
Positive Score
- Penalties
```

Clamp final result:

```text
0–100
```

These numbers are an initial calibration target.

Do not hardcode assumptions that prevent future adjustment.

Keep weights in a configuration object.

Example:

```ts
const SCORE_WEIGHTS = {
  commander: 0.25,
  theme: 0.20,
  roleNeed: 0.20,
  efficiency: 0.15,
  curve: 0.10,
  deckInteractions: 0.10
};
```

---

# 9. Add Negative Scoring

The current engine appears much better at finding reasons to award points than reasons to remove them.

Add explicit penalties.

Support at minimum:

```text
wrong_tribal_type
wrong_token_type
role_redundancy
mana_curve_congestion
poor_mana_efficiency
low_impact_card
unsupported_subtheme
requires_missing_enabler
win_more
nonbo
commander_noninteraction
duplicate_function
color_or_identity_issue
```

Suggested penalty range:

```text
Minor:      -2 to -5
Moderate:   -6 to -10
Major:      -11 to -20
```

The purpose is not to penalize every card lacking commander synergy.

`commander_noninteraction` should only be used when the card is being rewarded elsewhere as if it interacts with the commander.

---

# 10. Generic Tags Are Candidate Discovery Only

This is a critical rule.

Example:

```ts
candidate.tags.includes("tokens")
```

may cause a card to enter the token-related evaluation path.

It must NOT automatically result in:

```ts
score += 15;
```

Instead:

```text
Tokens detected
↓
What tokens?
↓
What does the deck reward?
↓
Do those token types match?
↓
Does the candidate trigger/pay off anything?
↓
Award points based on actual relationship
```

Apply the same logic to:

- Dragons
- Counters
- Sacrifice
- Graveyard
- Artifacts
- Lifegain
- Spellslinger
- Tokens
- Landfall

---

# 11. Recommendation Score Calibration

Use the following user-facing scale:

```text
90–100  Exceptional Fit
80–89   Excellent Fit
70–79   Strong Fit
60–69   Reasonable Fit
50–59   Situational
35–49   Weak Fit
0–34    Poor Fit
```

Important:

80+ should be difficult.

---

# 12. Excellent Fit Gate

A candidate may not receive `Excellent Fit` or higher unless at least one of the following is true:

### Condition A
Strong verified commander interaction.

OR

### Condition B
Strong verified interaction with at least two major deck themes/engines.

OR

### Condition C
Extremely high role need combined with excellent efficiency and no meaningful deck conflict.

This prevents generic playable cards from appearing as elite recommendations.

---

# 13. Confidence Score

Add recommendation confidence separately from synergy.

Example display:

```text
Synergy 78 — Strong Fit
Confidence: High
```

Suggested values:

```text
High
Medium
Low
```

High confidence should generally require:

- clear Oracle-text relationship;
- deterministic type/keyword interaction;
- known role classification;
- low ambiguity.

Medium confidence may be used when:

- interaction is inferred;
- synergy depends on deck-state assumptions;
- card has multiple conditional modes.

Low confidence may be used when:

- classification is incomplete;
- unusual rules interactions are involved;
- card text parsing is uncertain.

Do not mix confidence into the actual synergy score unless explicitly needed.

---

# 14. Evidence-Based Explanation System

Stop generating recommendation explanations primarily from broad tags.

The explanation must be built from the actual scoring evidence.

Store:

```ts
interface RecommendationEvidence {
  positives: string[];
  negatives: string[];
  commanderEvidence: string[];
  roleEvidence: string[];
  penalties: string[];
}
```

Then construct user-facing text from this evidence.

Example:

```text
Why it fits:
Counts as a Dragon because of changeling, so entering the battlefield
triggers Lathliss and creates a 5/5 Dragon. It also helps ensure future
land drops.

Concern:
The deck already has several cards at this mana value.
```

Do not produce unsupported language such as:

```text
"directly reinforces the Commander"
```

unless a stored commander interaction proves it.

---

# 15. "Why This Score?" Expansion

The existing expandable section should expose the components behind the final score.

Example:

```text
Commander interaction      23/25
Deck/theme synergy         16/20
Needed role                10/20
Card efficiency            11/15
Curve fit                   7/10
Deck interactions           8/10
Penalties                   -6

```

Exact visual layout can remain consistent with the existing app.

Do not expose excessive internal technical detail.

The point is user trust.

# 16. Improve Recommendation Summary Copy

Current explanation:

```text
Supports Dragon Typal, fills a needed tutor role, and directly
reinforces the Commander.
```

Problems:

- "Tutor" is over-broad.
- It hides the actual reason.
- It may claim direct Commander synergy without proof.

Preferred output:

```text
Counts as a Dragon through changeling, so it triggers Lathliss when it
enters. It also puts a basic land into your hand, helping you make
future land drops.
```

Specific mechanical explanation > generic role language.

---

# 17. Swap Candidate System

The app should not only determine:

> Is this card good?

It should also determine:

> What existing card is it realistically competing against?

For each recommended addition, generate one or more replacement candidates.

Compare:

```text
role overlap
mana value
theme contribution
commander synergy
card efficiency
redundancy
deck necessity
```

Prefer replacing cards that:

```text
share the same role
occupy similar curve space
score materially lower
are redundant
contribute less to the deck's core plan
```

---

# 18. Compare Screen

The existing `Compare [Card]` function should evolve toward:

```text
Candidate Card
vs.
Likely Cut
```

Example:

```text
Changeling Wayfinder
vs.
Dragon Egg
```

Comparison categories could include:

```text
Commander Interaction
Dragon Synergy
Card Advantage / Smoothing
Ramp / Mana Support
Defensive Utility
Mana Efficiency
Curve
Deck Need
```

The app should then explain the delta.

Example:

```text
Recommended swap:
Dragon Egg → Changeling Wayfinder

Why:
Wayfinder preserves the Dragon creature type while immediately
smoothing land drops and triggering Lathliss on entry.
```

Do not force a swap recommendation when confidence is low.

# 20. Add Additional Regression Cases

Do not rely only on the two above.

Create tests covering:

### Generic Removal
A strong removal spell with no commander synergy can still rank well if removal is needed.

### Wrong Tribal Token
A card creating Goblins/Soldiers in a Dragon deck must not receive Dragon-token bonuses.

### Tribal Changeling
Changeling must satisfy creature-type-based Dragon conditions.

### Land Search
Basic-land-to-hand must not be treated like unrestricted tutoring.

### Cost Reduction
Dragon-specific cost reduction should receive stronger tribal support than generic cost reduction when relevant.

### Generic Token Doubling
Determine whether the deck produces enough meaningful tokens before awarding high synergy.

### Unsupported Theme
A strong sacrifice card should score poorly if the deck lacks sacrifice engines.

# 22. Role Gap Analysis

Before evaluating owned cards, calculate the deck's needs.

Example:

```text
Ramp target: 10
Current: 7
Need severity: HIGH

Removal target: 8
Current: 6
Need severity: MEDIUM

Card draw target: 9
Current: 9
Need severity: LOW

Dragon payoff target: 6
Current: 7
Need severity: SATURATED
```

Recommendation scoring should reward cards according to actual need severity.

Do not reward another role simply because the card has that role.

---

# 23. Saturation / Redundancy Detection

A card should lose points when the deck already contains excessive quantities of the same function.

Example:

```text
Deck already has 14 five-mana Dragon payoffs.
Candidate is another five-mana Dragon payoff.
```

Even if thematic, it may be poor deck construction.

Possible penalty:

```text
curve congestion
role redundancy
```

---

# 24. Mana Curve Awareness

The engine should consider where the card sits in the current curve.

Do not just say:

```text
"The deck already has many cards at this mana cost."
```

Use that information in the score.

Example:

```text
Current MV3 count: 14
Target MV3 range: 8–11

Candidate MV: 3

Curve penalty: -4
```

Exact target modeling can evolve later.

Implement the architecture now.

---

# 25. Candidate Ranking

Recommended cards should be sorted primarily by:

```text
Final Score
```

Tie-breakers:

```text
1. confidence
2. commander interaction
3. role need
4. efficiency
```

Cards with major unresolved classification issues should not appear near the top simply because they have many overlapping tags.

---

# 26. Do Not Hardcode Individual Cards

Do not implement:

```ts
if (card.name === "Fire Nation Attacks") score -= 40;
```

or:

```ts
if (card.name === "Changeling Wayfinder") score += 20;
```

These are regression cases only.

The generalized engine must naturally produce the desired result.
