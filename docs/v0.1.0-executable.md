# MTG Manager v0.1.0 — Digital Binder Foundation
## Codex Implementation Executable

**Working product name:** MTG Manager\
**Release:** v0.1.0\
**Objective:** Build and deploy the visual/UI foundation of MTG Manager as a premium mobile-first digital Magic binder.\
**Scope discipline:** This release is an interface prototype with a clean future architecture. Do not build the intelligence engine yet.

---

# 0. Read This First

This is the first implementation of a long-term collection + Commander management application.

The mistake to avoid is overbuilding the product before the UI is proven.

For v0.1.0, optimize for:

> **“I want to open this app and browse my collection.”**

The application should look and behave like a premium collectible binder, not a generic dashboard.

Do not interpret the roadmap as permission to implement future features.

# 2. Recommended Technical Foundation

Use a modern, simple front-end stack.

Preferred:
- React
- TypeScript
- Vite
- modern CSS or Tailwind CSS
- Lucide icons or similarly lightweight icon set

Avoid unnecessary framework complexity.

For v0.1.0:
- no backend is required,
- no authentication is required,
- no database is required,
- state may be local/in-memory,
- sample collection data may live in the repository.

Architect components so a persistent data layer can replace sample data in v0.2.0 without rebuilding the UI.

# 3. Information Architecture

## Primary navigation

Use three top-level destinations:

### Collection
Active and fully implemented in v0.1.0.

### Commanders
Visible as a future destination. It may show a tasteful “Coming in a future release” state.

### Explore / Intelligence
Visible only if it helps establish the eventual IA. Do not build the intelligence feature itself.

On mobile, use a simple bottom navigation if it improves one-handed use.

Do not crowd the shell with settings or developer controls.

# 4. Collection Binder Screen

This is the hero experience of v0.1.0.

## Header

Show:
- product wordmark: `MTG Manager`
- current area: `My Collection`
- total sample cards / unique cards in subtle secondary text
- search affordance
- filter affordance

Keep the header compact on mobile.

## Search

A user should be able to search sample cards by name.

Requirements:
- immediate filtering,
- clear/reset control,
- keyboard-friendly,
- large enough touch target on phone.

## Quick filter chips

Provide horizontally scrollable chips on mobile.

Suggested initial chips:
- All
- White
- Blue
- Black
- Red
- Green
- Multicolor
- Colorless
- Creatures
- Artifacts
- Enchantments
- Lands

If sample metadata includes basic strategy tags, it is okay to add a small “Synergy” filter section for demonstrating the future experience, but do not build automated tagging.

## Filter drawer

A filter button should open a mobile-friendly bottom sheet / drawer.

Support UI controls for:
- color identity,
- card type,
- mana value range,
- rarity,
- set,
- foil,
- sample synergy tag if present.

Filters must visibly indicate when they are active.

Provide:
- Clear all
- Apply

## Sort

Support at minimum:
- Name A–Z
- Mana value
- Color
- Set

Do not add market-price sorting in v0.1.0.

# 5. Card Grid

The collection should feel like a binder page.

## Desktop
Target approximately 5–7 cards per row depending on viewport.

## Tablet
Target approximately 3–5 cards per row.

## Mobile
Default to 2 cards per row.

Allow the grid to breathe. Card art must remain large enough to enjoy.

## Card tile behavior

Each card tile should:
- primarily display card artwork,
- maintain Magic card proportions,
- use subtle elevation/border treatment,
- show quantity with a small unobtrusive badge if quantity > 1,
- optionally show foil indicator,
- have a pressed state on touch,
- avoid putting large text overlays on the artwork.

On desktop:
- subtle hover lift/scale is acceptable.

On mobile:
- no interaction should depend on hover.

Tap/click opens the Card Detail view.

---

# 6. Card Detail View

Use:
- bottom sheet / near-full-screen drawer on mobile,
- modal or side drawer on desktop.

The detail experience should feel visually premium.

Show:
- large card artwork,
- card name,
- mana cost / mana value,
- color identity,
- type line,
- set,
- rarity,
- owned quantity,
- foil state where applicable.

If oracle text is included in the local sample dataset, display it in a readable section.

## Future-intelligence preview

Include a restrained section called:

**Card Intelligence**

For v0.1.0 this may show **manually authored sample tags** only, for example:
- +1/+1 Counters
- Landfall
- Tokens
- Ramp

Clearly architect these tags as sample metadata rather than pretending an intelligence engine exists.

A subtle label such as `Preview` is appropriate.

Do not generate recommendations.

---

# 7. Sample Data

Use a small but varied sample collection, roughly 24–40 cards.

The sample data should demonstrate:
- all five colors,
- multicolor,
- colorless/artifacts,
- lands,
- multiple mana values,
- several card types,
- multiple sets,
- quantities above 1,
- a few foils,
- several manually assigned strategy tags.

Include cards that make the future semantic filtering concept obvious, such as examples that naturally represent:
- +1/+1 counters,
- landfall,
- tokens,
- graveyard,
- artifacts,
- ramp,
- card draw,
- removal.

Prefer Scryfall IDs as the canonical IDs in the sample records.

Do not hammer the Scryfall API on every render.

For this prototype, either:
1. commit a small normalized sample JSON dataset with image URLs, or
2. fetch a small dataset once and cache it locally.

Do not make dozens of per-card API calls during normal rendering.

# 8. Visual Direction

## Overall feel

Keywords:
- premium binder,
- dark collector's table,
- cinematic but restrained,
- tactile,
- sophisticated,
- card-art-forward.

Avoid:
- generic SaaS blue,
- giant analytics tiles,
- spreadsheet styling,
- excessive gradients,
- fantasy fonts for body text,
- fake leather textures that reduce readability,
- over-ornamentation.

## Suggested visual system

Background:
- deep neutral charcoal/obsidian.

Surface:
- slightly raised dark panels,
- soft borders,
- restrained transparency.

Typography:
- clean modern sans-serif for functionality,
- optional elegant display face for the wordmark only.

Accents:
- warm metallic / parchment-inspired accent may be used sparingly,
- Magic color identities may appear in filter states or tiny indicators,
- do not let five-color UI become visually noisy.

Artwork:
- should dominate the collection view.

## Motion

Use small transitions:
- card press/hover,
- drawer entrance,
- filter selection,
- page transitions if present.

Motion should feel polished, not game-like.

Honor reduced-motion preference.

# 12. Interaction Requirements

### Searching
Typing updates results immediately.

### Filtering
Multiple filters can coexist.

### Active filter state
The UI must make it obvious that the collection is filtered.

### Reset
One action restores the full collection.

### Card opening
Tap card → detail appears quickly and smoothly.

### Browser navigation
If routing is used for card details, back behavior must feel natural.
If a modal/drawer is used, browser back should not produce strange state.

### No-results
Show a polished message and a clear reset action.

---

# 13. Performance Rules

The binder should remain smooth on a normal phone.

Requirements:
- lazy-load card imagery where practical,
- include image dimensions/aspect ratio to prevent layout shift,
- avoid excessive re-rendering,
- do not download unnecessary high-resolution images for tiny thumbnails,
- do not issue an API request per card on each app load,
- use memoization only where it solves an observed issue,
- keep dependencies modest.

---

# 14. Accessibility Baseline

- semantic buttons,
- accessible labels for icons,
- visible keyboard focus,
- sufficient text contrast,
- dialog/drawer focus management,
- Escape closes desktop modal where appropriate,
- meaningful image alt text,
- reduced-motion support.

# 16. Acceptance Criteria

v0.1.0 is complete only when all of the following are true.

## Functional
- App loads without console errors.
- Sample collection renders.
- Search works.
- Color filter works.
- Card-type filter works.
- At least one additional filter works.
- Sorting works.
- Clear/reset works.
- Card detail opens/closes reliably.
- Empty state works.

## Mobile
- 2-column card grid works around 390 px width.
- No page-level horizontal overflow.
- Search/filter controls are comfortable to use.
- Detail drawer is readable without microscopic text.
- Navigation does not cover content.
- iOS safe-area behavior is acceptable.

## Desktop
- Grid uses the available width gracefully.
- Card detail is not awkwardly stretched.
- Hover behavior is optional enhancement, never required.

## Visual
- Card artwork is visually dominant.
- UI does not resemble an admin dashboard.
- Typography hierarchy is clear.
- Filter state is understandable.
- The experience feels coherent from collection → card detail → back.

## Engineering
- TypeScript compile/build succeeds.
- Lint passes if lint is configured.
- Production build succeeds.
- README explains local development and deployment.
- No secrets committed.
- Future collection persistence can replace sample data without rewriting the entire UI.
